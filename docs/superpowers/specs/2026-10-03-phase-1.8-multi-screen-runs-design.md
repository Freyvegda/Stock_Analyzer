# Phase 1.8 — Multi-screen runs + stock "Criteria pass" accordion (design)

**Date:** 2026-10-03
**Status:** Approved in conversation (owner), pending implementation
**Branch:** `phase-1.8`
**Prerequisite:** Phase 1.7 complete on this branch (merge `ff4fa6e`) — `screening_sets` with exactly
one active set per user, `screen_runs.set_id` written, `/screen/latest` and the stock report scoped
to the active set.

## 1. Intent

Two connected outcomes:

1. **One Run Screen, four screens evaluated.** When the user runs their active screen, the run also
   evaluates the three other screens they use most, so those stay current without manual switching.
2. **A stock shows its pass/fail against all four.** The stock detail page replaces the single
   report card with a "Criteria pass" accordion: the active screen plus the three most-used screens,
   each with a live report for that stock.

"Most used" is measured from the user's own behaviour, not from the automatic runs: the frequency
of screens across the last 10 **manually triggered** runs.

## 2. Owner decisions (2026-10-03)

| Question | Decision |
|---|---|
| Scope/dependency | Phase 1.7 lands first (merged into `phase-1.8`); feature is part of Phase 1.8 |
| Which runs count | Last 10 user-triggered runs, counted once per run batch (the active screen). Auto-runs excluded — no self-reinforcement |
| Accordion content | Live per-screen report (verdict, criteria rows, notes), computed from the stored snapshot; never persisted |
| Extra 3 screens | Actually execute + store as runs (`triggered_by='auto'`); reuse the active run's prepared snapshot; zero extra network |
| Batch mechanics | One prepare stage, then evaluate + store up to 4 screens on the same candidates (orchestrator, not a loop over `run_screen`) |

## 4. Most-used selection

`app/screener/service.py`:

```python
def most_used_sets(session_factory, user_id: int, limit: int = 3, exclude_id: int | None = None) -> list[dict]
```

1. Take the caller's last `10` runs with `triggered_by == 'manual'`, newest first, keep their
   `set_id`s.
2. Count occurrences per set id.
3. Keep only sets that still exist (deleted screens have their runs' `set_id` nulled by 1.7, so they
   drop out naturally) and `id != exclude_id`.
4. Order: count desc → most recent manual run desc → set id asc. Cut at `limit`.

Returns `_projection`-shaped dicts (id, name, criteria, thesis, shortlist_size, is_active,
updated_at). Fewer than 3 candidates → fewer extras; no history → none.

The run batch and the stock accordion both call this helper, so they can never disagree.

## 5. Run batch (backend)

`app/screener/service.py` refactor:

- `_prepare(provider, session_factory)` — today's `run_screen` stages 1–2: upsert `stocks`, gate the
  stored snapshot, refresh only stale symbols (per-stock isolation), upsert `fundamentals` +
  profiles, build `candidates`. Returns `{today, candidates, failed_symbols, total, stale_provider}`.
- `_evaluate_and_store(session_factory, user_id, prepared, criteria, shortlist_size, set_id,
  triggered_by)` — today's stages 3–4: `screen_rows` → `rank_shortlist` → insert one `ScreenRun`
  with the criteria snapshot and `triggered_by`. Returns the active-shape result dict.
- `run_screen(...)` — public wrapper, unchanged signature; `_prepare` + `_evaluate_and_store`
  (`manual`). Kept for compatibility and direct callers.
- `run_screen_batch(provider, session_factory, user)`:
  1. active set (`get_active_set`), `_prepare` once;
  2. evaluate + store the active set (`manual`);
  3. `most_used_sets(exclude=active.id)`;
  4. for each, `_evaluate_and_store` (`auto`) inside its own `try/except` — one extra failing never
     kills the batch or the other runs; failure is reported as `error` on that entry;
  5. return the active result plus `extra_runs`.

All four evaluations see the identical `candidates` list → one snapshot per batch.

`app/api/screen.py`: `POST /screen/run` calls `run_screen_batch`.

### Response

```json
{
  "run_id": 12, "shortlisted": [], "failed_count": 0, "failed_symbols": [],
  "failed_details": [], "stale": false, "total": 500,
  "extra_runs": [
    {"set_id": 3, "name": "Quality", "run_id": 13, "shortlisted": 7, "error": null},
    {"set_id": 4, "name": "Value", "run_id": 14, "shortlisted": 0, "error": "..."}
  ]
}
```

`extra_runs` is `[]` when there is no history or no other set.

## 6. Stock detail (backend)

`GET /stock/{symbol}` (and `POST /stock/{symbol}/refresh`) replace `report` with:

```json
"reports": [
  {"set_id": 1, "name": "Default", "is_active": true,  "report": { "...StockReport..." }},
  {"set_id": 3, "name": "Quality", "is_active": false, "report": { "...StockReport..." }}
]
```

- Built per request from the stored snapshot + each set's criteria via the existing pure
  `report.build_report`; never persisted.
- Active first, then `most_used_sets(limit=3, exclude_id=active.id)`.
- `run` chip: `stock/service.py::_latest_run_entry` must filter
  `ScreenRun.set_id == active.id` — with auto-runs stored, the user's newest run can belong to
  another screen.
- `/stocks` universe verdict chips stay active-only (out of scope).

## 7. Frontend

- `src/api/types.ts`: `ScreenRunResult` gains
  `extra_runs?: {set_id: number; name: string; run_id: number | null; shortlisted: number | null; error: string | null}[]`;
  `StockDetail.report` → `reports: StockScreenReport[]` (`{set_id, name, is_active, report}`).
- New `components/StockReportsAccordion.tsx`: Chakra `Accordion.Root multiple`. Items in API order;
  header = screen name + `Active` badge (first item) + Pass/Fail badge; body = score line, criteria
  rows (value vs threshold, pass/fail glyph + sr-only text), notes — the current
  `StockReportCard` body becomes the item body. Active item expanded by default, others collapsed.
  Empty criteria keeps the `No criteria enabled` copy.
- `pages/StockDetail.tsx` renders `reports` through the accordion. `StockReportCard.tsx` and its
  tests are superseded by the accordion (single-report rendering no longer exists).
- `pages/fundamentals/TopTen.tsx` (where the run lands after the auto-jump): a small
  `Also ran: Quality (7) · Value (failed)` line under the summary, sourced from `extra_runs` in
  the layout context; no `extra_runs` renders nothing. Failed extras show `(failed)`.
- Top 10 keeps showing the active screen's run only; auto-runs never surface there.

## 8. Error handling

- `_prepare` failures keep today's behaviour (per-stock isolation; provider errors ride existing
  handlers).
- Each extra run is isolated; its failure is caught, logged, and reported in `extra_runs[].error`.
  The active result always returns 200 when the active evaluation succeeded.
- A corrupt/unknown set criteria payload falls back via `criteria_from_json` exactly as today.
