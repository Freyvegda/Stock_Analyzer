# Phase 1.5 — Authorization, DB-Driven Per-User Screener, Criteria Editor, Stair-Tower Loader

**Date:** 2026-09-26
**Status:** Approved (design reviewed in session)
**Scope:** `backend/` + `frontend/` + database. Builds on Phase 1.

## Intent

Phase 1 shipped a working fundamentals screen driven by `backend/config/screening.yaml`.
Phase 1.5 makes the tool personal and user-owned:

1. **Authorization** — the app is gated behind a login. First visit creates the one account
   (single-user, multi-user-ready schema); afterwards everything requires a session.
2. **Screener config moves to the database, per user** — the YAML file is retired. Each user
   owns a criteria set (stored as JSON) plus a free-text thesis note, and every screen run
   uses the caller's criteria.
3. **Criteria become dynamic** — user can add any numeric yfinance-backed ratio, with
   on/off toggles, thresholds, and an autocomplete lookup. Existing six ratios remain the
   defaults.
4. **Edit Criteria subwindow** — animated dialog from the Criteria panel; where the user
   shapes the screen.
5. **Fixed top-10** — the user cannot change how many stocks one run produces. Backend
   clamps to 10; UI shows a read-only `Top 10` badge.
6. **Stair-tower loader** — a pure-CSS, never-ending staircase animation used while a screen
   runs and in small control surfaces (login, dialog save).

Success criteria:

- First visit → setup card → account created → logged in; reload keeps session (30 days).
- All pipeline routes (API + UI) require auth; 401 anywhere bounces to `/login`.
- Criteria edit → save → run uses exactly those criteria; snapshot stored on the run.
- Any catalog ratio can be added/removed/toggled; unknown keys rejected with 422.
- `backend/config/screening.yaml` and `/screen/config*` endpoints no longer exist.
- Loader renders the tower animation, freezes to a static pose under reduced motion.
- `pytest` green offline, `npm run test` green offline, `npm run build` clean.

## Constraints

- `backend/BACKEND.md`, `frontend/FRONTEND.md`, `backend/app/db/DATABASE.md`, and
  `frontend/DESIGN.md` are binding context; update them in the same change.
- Budget stays ₹0: no paid services, no external auth provider, no new SaaS.
- Tests run offline: mock all network. Session cookies created directly in test helpers.
- Schema stays Postgres-compatible; dev DB is disposable (delete file → `init_db()` rebuilds).
- `pip install` on this machine always uses `--isolated`.
- Node/npm unchanged; no new frontend dependency for the loader (pure CSS + existing Chakra).

## Decisions (locked in review)

1. **Single account, multi-user-ready schema.** `users` table holds one row in practice;
   `user_criteria` and `screen_runs` are already keyed by `user_id`.
> **Superseded by Phase 1.8 (2026-09-29).** Decision 2 below is no longer how the app
> authenticates: `SessionMiddleware` and the `sa_session` cookie were replaced by a 15-minute
> HS256 access token in memory plus a rotating opaque refresh token in an HttpOnly `sa_refresh`
> cookie, with an `auth_sessions` table. The current contract is in `backend/BACKEND.md` and
> `backend/app/db/DATABASE.md`. This spec is kept as the record of what was decided then.

2. **Session = signed HttpOnly cookie** via Starlette `SessionMiddleware`
   (`itsdangerous`), cookie name `sa_session`, payload `{user_id, username}`, `max_age`
   30 days, SameSite=lax, `Secure=False` (local http). Signing secret = 32 random bytes
   (`secrets.token_urlsafe(32)`) persisted at `data/.session_secret` (gitignored, created on
   first use; deleting/rotating it invalidates all sessions). No sessions table. Logout
   clears the cookie.
3. **Password hashing = stdlib `hashlib.scrypt`** (n=2^14, r=8, p=1), 16-byte random salt,
   format `scrypt$n$r$p$<salt_b64>$<hash_b64>`, verified with `secrets.compare_digest`.
   No passlib/bcrypt/authlib. Password min length 8.
4. **First-run setup screen**: `GET /auth/state` → `{users_exist: false}` renders the setup
   card; `POST /auth/setup` creates the account and logs in (409 if a user already exists —
   handles the two-tab race).
5. **Criteria JSON per user** (shape below), plus `thesis` (≤ 500 chars) and
   `shortlist_size` (server-set, clamped to 10; never accepted from the client).
6. **Dynamic ratio catalog, code-owned** (`app/screener/catalog.py`). Only catalog keys are
   valid; direction (`min`/`max`) is fixed per entry. Values resolve from normalized columns
   (`derived`) or the stored `raw_json` payload (`raw`). Missing/NaN → criterion fails, same
   as Phase 1.
7. **YAML retirement**: delete `backend/config/screening.yaml`, `app/screener/config.py`,
   and the `GET /screen/config` + `POST /screen/config/reload` endpoints. `ConfigError` stays
   as the 422 vehicle for criteria validation.
8. **Per-user data**: `user_criteria` + `screen_runs` only. `stocks`, `fundamentals`,
   `prices`, `documents`, `signals`, `backtest_runs` stay global/shared.
9. **Loader = "never-ending tower"** (variant 3): 8 step cells in two columns spawn at the
   top and fall away while an emerald dot climbs forever, zig-zagging between columns.
   Pure CSS keyframes; one CSS file scales from 16px to 140px; no JS animation.
10. **Loader placement**: replaces the Three.js `RunVisual` in the run card (~120px) and
    appears at ~20px inside the login submit and the dialog save buttons. `AmbientField`
    background stays. `RunVisual.tsx` + its test are deleted.
11. **`DESIGN.md` exception**: the loader is the single sanctioned continuous/looping
    animation in the app, and it is never rendered inside data areas (tables, summaries).

## API contract

All routes below require a session except `/health` and `/auth/*` login/state routes.

### Auth

| Method + path | Auth | Body | Success | Errors |
|---|---|---|---|---|
| `GET /auth/state` | public | — | `{users_exist: bool, user: {id, username} \| null}` | — |
| `POST /auth/setup` | public | `{username, password}` | 201 `{user}` + session cookie | 409 if a user exists; 422 short password/username |
| `POST /auth/login` | public | `{username, password}` | 200 `{user}` + session cookie | 401 `Invalid username or password` (generic, no enumeration) |
| `POST /auth/logout` | session | — | 204, cookie cleared | 401 |
| `GET /auth/me` | session | — | `{id, username}` | 401 `Not authenticated` |

### Screen

| Method + path | Body | Success | Errors |
|---|---|---|---|
| `GET /screen/ratios` | — | `[{key, label, unit, category, direction}]` (catalog) | 401 |
| `GET /screen/criteria` | — | `{criteria: [...], thesis, shortlist_size}` (seeds defaults first read) | 401 |
| `PUT /screen/criteria` | `{criteria: [...], thesis?}` | saved `{criteria, thesis, shortlist_size}` | 401, 422 |
| `POST /screen/run` | — | `{run_id, shortlisted, failed_count, failed_symbols, failed_details, stale, total}` | 401 |
| `GET /screen/latest` | — | caller's latest run + enriched rows | 401, 404 no run |

Validation rules for `PUT /screen/criteria` (pydantic, `extra="forbid"`):

- `criteria`: 1–50 items; every `key` in `RATIO_CATALOG`; no duplicate keys; `enabled` bool;
  `value` finite float (negatives allowed — growth can be negative).
- At least one item with `enabled: true`.
- `thesis`: optional, ≤ 500 chars.
- `shortlist_size` in the request → 422 (server-owned).
- Any violation → 422 with a human-readable `detail`.

Removed: `GET /screen/config`, `POST /screen/config/reload`.

## Ratio catalog

`app/screener/catalog.py` owns a `RATIO_CATALOG: list[RatioSpec]` where

```python
RatioSpec = {
  "key": str,          # stable id stored in criteria JSON, e.g. "forwardPE"
  "label": str,        # human label, e.g. "Forward P/E"
  "yf_field": str|None,# raw .info key when source="raw"
  "source": "derived" | "raw",
  "direction": "min" | "max",   # fixed; UI renders ≥ / ≤
  "scale": float,      # applied to raw values (fraction -> percent etc.)
  "unit": str,         # "%", "×", "₹ cr", "₹"
  "category": str,     # "Valuation", "Profitability", ...
}
```

- `derived` entries = the six existing normalized values (`pe, pb, roe, roce,
  debt_to_equity, market_cap`), read from the row (never from `raw`).
- `raw` entries are read as `row["raw"].get(yf_field)` then multiplied by `scale`; the full
  `.info` payload is already persisted in `fundamentals.raw_json`.
- Non-numeric, missing, or NaN raw values → `None` → criterion fails. Catalog contains only
  numeric `.info` fields; string fields (e.g. `sector`) are unrepresentable by design.
- Starter `raw` set (~26): `forwardPE`, `pegRatio`, `priceToSalesTrailing12Months`,
  `enterpriseToEbitda`, `enterpriseToRevenue`, `priceToFreeCashflow`, `returnOnAssets`,
  `profitMargins`, `operatingMargins`, `grossMargins`, `ebitdaMargins`, `revenueGrowth`,
  `earningsGrowth`, `earningsQuarterlyGrowth`, `currentRatio`, `quickRatio`, `beta`,
  `trailingEps`, `forwardEps`, `bookValue`, `revenuePerShare`, `dividendYield`,
  `payoutRatio`, `fiveYearAvgDividendYield`, `heldPercentInstitutions`, `heldPercentInsiders`.
- Scales are guesses until verified: one implementation task checks each `raw` entry against
  live yfinance for 2–3 tickers and pins the correct scale/unit in the catalog (mismatch is
  fixed in the catalog, never by mutating stored data).

## Engine changes

`evaluate_screen(rows, criteria) -> (shortlist, rejected)`:

- Iterates only `enabled` criteria; a stock passes when every enabled criterion passes
  (`min`: value ≥ threshold, `max`: value ≤ threshold; `None` fails).
- Rejected entries keep the Phase-1 shape: `{"symbol": ..., "failed": [criterion keys]}`.
- Ranking formula unchanged: `score = roe + roce − 20 × debt_to_equity` (missing → 0);
  sort desc; cut at `min(shortlist_size, 10)`.
- Shortlist rows keep `{rank, symbol, score, ratios, failed: []}`; `ratios` now contains only
  the six derived keys that exist as columns, unchanged for the existing table.

`service.run_screen(provider, session_factory, user, criteria, shortlist_size)`:

- Fetches + persists fundamentals exactly as Phase 1 (per-stock isolation).
- Evaluates with the caller's criteria; stores `user_id` + `criteria_json` snapshot.

## Frontend component specs

### AuthContext + RequireAuth + Login page

- `AuthProvider` calls `GET /auth/me` on mount (401 = anonymous, no error state).
- `RequireAuth` renders children when a user exists, otherwise `<Navigate to="/login" />`.
- `/login` calls `GET /auth/state`:
  - `users_exist: false` → **Create account** card (username, password, confirm; client-side
    rules mirror backend: username 3–32, password ≥ 8, confirm matches).
  - otherwise → **Login** card.
  - Success → refetch auth state → navigate to `/`; 401/409/422 detail rendered inline in
    `role="alert"`; submit button hosts the 20px stair-tower loader while pending.
- `api/client.ts` gains `put`, and on any 401 throws `ApiError` after dispatching
  `window.dispatchEvent(new Event('auth:unauthorized'))`; `AuthProvider` listens, clears the
  user, and `RequireAuth` redirects. Login/setup calls are exempt from the event (handled
  locally).

### CriteriaPanel (modified)

- Read-only badges for enabled criteria only, using catalog labels and units
  (`PE ≤ 25`, `ROE ≥ 15%`, `Dividend Yield ≥ 1%`, unknown keys fall back to `key: value`).
- `Top {shortlist_size}` badge stays (read-only).
- New primary `Edit Criteria` button opens `CriteriaDialog`; the YAML hint and reload button
  are removed. Panel loads from `GET /screen/criteria`.

### CriteriaDialog (new)

- Chakra `Dialog.Root` with `motionPreset="scale"` open/close transitions; backdrop fade;
  body scrollable (`maxH="70vh"`); each criterion row enters with a short staggered
  transition via `motion` (reduced-motion → instant).
- Row = enable `Switch` + label (`unit`) + numeric `Input` + remove icon button; disabled
  rows dim; direction suffix (≥ / ≤) shown from the catalog.
- **Add ratio**: Chakra Combobox fed by `GET /screen/ratios`, fetched once per dialog open,
  filtered locally (case-insensitive match on label/key), grouped by category, existing keys
  excluded; selecting adds an enabled row with an empty value.
- Thesis `Textarea` (count/limit 500).
- Footer: Cancel + Save; Save shows the 20px tower loader while `PUT` is in flight.
- Client validation mirrors the API (every row numeric/finite, ≥ 1 enabled, thesis length);
  per-row errors + top-level `role="alert"`; success toast and panel refresh from the
  response; dialog closes on success only.
- `GET /screen/criteria` failure on open → inline error with Retry, dialog never blank.

### StairTowerLoader (new)

- `StairTowerLoader({ size = 120, label = 'Loading…', className })`.
- Structure: wrapper `role="status"` (`aria-live="polite"`, visually-hidden label text) +
  8 step elements (2 columns) + 1 dot element. All animation in `stair-tower.css`.
- CSS: `--tower-size` custom property drives every dimension in `em`/`calc`, so the same file
  renders 16px (buttons) through 140px (run card). Steps loop: spawn top (`opacity 0 →
  1`, translateY −16px) → fall away bottom (`opacity → 0`, translateY ~214px at 1×), 8
  negative animation delays offset them into a seamless infinite stream. Dot: `translateY`
  bottom → top over the same cycle, plus a two-column zig-zag via a stepped X animation.
- `prefers-reduced-motion: reduce` → all animations `none`, dot frozen mid-tower, steps in
  a static pattern (still meaningful markup, no motion).
- Used at 120px in the run card (replaces lazy `RunVisual`) and 20px inside login/setup and
  dialog-save buttons (passed through Chakra Button's spinner slot when available, otherwise
  rendered inside the button content).
- Tests assert DOM structure, `role="status"`, and reduced-motion static behavior via
  mocked `matchMedia`; CSS animation itself is not asserted in jsdom.

## Error handling

- **401 everywhere** → JSON `{"detail": "Not authenticated"}`; frontend event → redirect.
- **Setup race** (second tab) → 409 `Account already exists`; login page shows the message
  and switches to the login card.
- **Criteria validation** → 422 with detail; the dialog maps row-level failures when possible
  and otherwise shows the detail banner.
- **Catalog field missing for a stock** → stock fails that criterion and appears in
  `failed_details` with the key; run continues (Phase-1 isolation unchanged).
- **Secret file deleted/invalid** → sessions verify-fail → 401 → login (acceptable).
- **Session expiry mid-run** → the synchronous run completes and is stored; the next request
  returns 401 and the UI redirects.

## Review focus (edge cases the tests must pin)

1. Two-tab setup race → 409 handled, UI recovers to login card.
2. Missing raw catalog field for some stocks → only those stocks fail that criterion.
3. Tampered/oversized `shortlist_size` in DB → engine clamps to 10.
4. `PUT` with `shortlist_size` present → 422 (client cannot set record count).
5. Session cookie tampered/expired → 401 → clean redirect, no crash, no loop.
6. API failure while dialog loads criteria → inline error + retry, dialog never blank.
7. Reduced-motion users → loader static, dialog transitions instant.
8. Disabled criteria never affect pass/fail and are never rendered as active badges.
